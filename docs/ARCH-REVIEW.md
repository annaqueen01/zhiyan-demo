# 《经管论文助手》纯前端 Demo —— 产品架构评审（从严）

评审视角：产品架构评审人（不是方案背书人）。
评审对象：一个**仅交付前端**、**不自建后端**、**不持有任何密钥**、能在浏览器里跑通可信核心流程的 AI 产品 demo。
核心能力声称（四块）：① 实证研究设计与代码生成/执行 ② 论文撰写 ③ 部分可可视化解释 ④ 学习模式（划词追问 + 解读已发表论文）。

> 评审基调：先判定"这个 demo 到底证明了什么"，再谈技术。技术选型可以换，叙事不成立就全盘皆输。

## 0. 评审结论（先给判决）

| 维度 | 判决 | 一句话理由 |
|---|---|---|
| 主流程是否成立 | **成立，但必须收窄** | "上传 300 篇本地 PDF → 持久索引 → 章节级引文映射 → 四块能力"是一条自洽的链，前提是把"生成"降级为"有据可查的组装"。 |
| 纯前端约束是否致命 | **不致命，但代价被低估** | 致命点不是"跑不动模型"，而是"索引构建时长"与"存储被驱逐"这两件事会摧毁可信度。 |
| 四块能力同权 | **不成立** | 四块同权 = 没有重点。必须立一块为唯一主流程，另外三块是它的三种输出形态。 |
| "AI"是否诚实 | **取决于是否敢在 UI 上写清推理位置** | 本地推理（WebGPU/WASM）+ 模板组装 + 逐段出处，三者都真做，就诚实；任何一处偷偷调云、或把模板说成模型，就崩。 |
| 最大风险 | **不是技术，是"可核查的幻觉"** | 一个看起来严谨、结果却不可复现的"实证代码生成"，比明确说"我不会"更伤产品。 |

**一句话定位建议**：
> 这不是"AI 写论文"，是**"以你自己上传的文献库为唯一事实来源、逐句可回溯出处的写作与研究工作站"**。
> 卖点是**可核查（verifiable）**，不是**智能（smart）**。

## 1. 单一主流程，以及 MVP / 演示 / 非承诺的边界

### 1.1 唯一主流程（One Flow，必须只有一个）

```
选一个文件夹（≤300 篇 PDF）
  → 本地解析 + 结构识别 + 分块 + 建索引（可中断、可续跑、进度可见）
  → 生成"语料体检报告"（哪几篇能救、哪几篇废了）   ← 这一步是信任的起点
  → 建立"章节 ↔ 参考文献"映射表（用户可手改）
  → 在某一章里工作：检索片段 → 提纲 → 逐段起草（每段带 citation chip）
  → 点击 chip 回跳原 PDF 的那一页那一块 + 可导出证据表
```

这条链里，**唯一的"用户可见核心动作"是：从"我有一堆 PDF"到"我这一章有了可核查的初稿骨架"**。
其余三块能力不是并列模块，而是这条链上的**三个输出形态**：

- 实证代码生成/执行 = 在"我这一章"里插入一段可复现的分析流水线；
- 可视化解释 = 对"我这一段结论"配一张图 + 图注自动引用来源；
- 学习模式（划词追问 / 解读已发表论文）= 把链条倒过来跑，但用的是同一个索引、同一套出处机制。

> **评审意见**：把"学习模式"做成独立 Tab 是个陷阱。它是同一个检索内核的另一种入口，独立 Tab 会导致两套 UI、两套引用逻辑、两倍验收成本。

### 1.2 MVP（值得作为 demo 验收的核心）

| # | MVP 项 | 验收标准（可观测、可复现） |
|---|---|---|
| M1 | 批量 PDF 入库 + 持久化 | 断开页面/重启浏览器，索引仍在；重复上传同一文件**不重算** |
| M2 | 逐篇抽取质量诊断 | 每篇给出 文本覆盖率/乱码率/疑似扫描件/双栏风险 四个指标，并明确分级 |
| M3 | 结构化分块 + 章节映射 | 每块有 `doc_id/page/bbox/char_range`；章节映射可人工纠正并留痕 |
| M4 | 混合检索（关键词 + 语义） | 关键词可用时即可用；语义未就绪不阻塞主流程 |
| M5 | 检索式起草（含逐段出处） | 每段草稿的每个 citation chip 可回跳原页高亮 |
| M6 | 导出证据包 | 一键导出 引用表.csv + 草稿.md + 分析脚本.py + 数据哈希 + 环境锁文件 |

### 1.3 演示级（Demo-only：证明"技术上通了"，但不承诺质量）

- 本地小模型生成自然语言段落（WebLLM / transformers.js）：**只承诺"离线可生成"，不承诺"达到可投稿质量"**。
- Pyodide 跑固定效应/聚类标准误/DiD/事件研究：**只承诺"脚本可复现、系数可复算"**，不承诺覆盖所有计量设定。
- 划词追问：**只承诺"答案必带出处，无出处则明确说无法回答"**（拒答是一个特性，要专门做）。
- 已发表论文解读：**只承诺"结构化抽取表"**（研究问题/数据/识别策略/结论/局限），不承诺"审稿级批判"。

### 1.4 明确**不做**（非承诺能力，请在 UI 与 README 里写死）

1. **不联网抓取知网/任何第三方全文**。产品定位为"用户自带语料的本地工作台"，不是文献获取工具。这也正好规避合规风险——要在产品说明里主动声明。
2. **不做查重、不做降重**。没有权威比对库，做了就是骗人。
3. **不承诺"零幻觉"**。只承诺"每个论断都能回跳出处；无出处的内容一律显式标注为『无来源·待核实』"。
4. **不承诺跨设备同步**。纯本地 + 手写 key 的加密导出包是唯一同步路径。
5. **不承诺 100% 版式正确的 PDF 解析**。300 篇里必然有解析失败的；产品承诺的是"失败是可发现、可标注、可手工补救的"。
6. **不把 300 篇全部塞进上下文**。任何"整库问答"都必须是"检索→片段→引用"。

> **评审意见**：把 1.4 直接做成产品内的一页"能力边界说明书"。这是这个 demo 最便宜的信任杠杆——**主动暴露边界的产品，评委默认它别处没吹牛**。

## 2. 浏览器内 PDF 批量处理 / 结构化 / 检索 / 持久化：选型 + 量化预算 + 降级

### 2.1 数据流（贯穿全链的关键 ID）

```
File(handle)
 ├─ 指纹 doc_id = SHA-256(size + 首尾 1MB + 文件名)     ← 去重靠它，不靠文件名
 ├─ 校验：magic bytes %PDF- / 加密位 / 页数上限
 ├─ 队列：并发 1~2 个 Worker（IO 与 CPU 争抢，别贪心）
 ├─ 抽取：pdf.js → getTextContent() → items[{str, transform, width, height}]
 ├─ 诊断：coverage = 抽到字符数 ÷ 页面积估算；乱码率 = 非预期码点占比
 │        if coverage 过低 → 标记扫描件 → OCR 路由（tesseract.js，默认不自动跑，需用户确认）
 ├─ 归一化：连字符换行、行内断行、CJK 间多余空格、连字(ﬁ)、页眉页脚剥离
 ├─ 结构：字号/加粗聚类 → 标题层级 → 参考文献段识别
 ├─ 分块 chunk = f(段落, ~350–700 中文字, 重叠 15%, 不跨章节)
 │        chunk_id = hash(doc_id + char_range + 文本哈希)
 ├─ 索引：BM25(字符二元组) 倒排 + 向量(Int8 量化)  → 混合 RRF 融合 → 可选 MMR 去冗
 └─ 映射：章节 → 候选文献（BM25 + 向量 + 参考文献显式提及）→ 打分表（用户可改）
```

**为什么 `chunk_id` 用内容哈希**：这是"可续跑"和"幂等"的地基。任一步崩了，重启只重算缺失的 chunk。这一点比选哪个索引库重要一个数量级。

### 2.2 选型表（含"为什么不是别的"）

| 层 | 选型 | 量化预期 | 为什么不选替代 |
|---|---|---|---|
| PDF 文本抽取 | **pdf.js（Worker 内）** | 纯文本页 ~50–200 页/秒；>100MB 文件必须分页流式取，禁止整文件读入 ArrayBuffer | 不用 pdfjs-dist 主线程版（UI 冻结）；不用服务端解析（约束不允许） |
| 扫描件 OCR | **tesseract.js（chi_sim 语言包）** | 1–5 秒/页（视分辨率），语言包 +30MB 级下载 | 默认**不自动触发**：300 页扫描件 = 十分钟级，必须用户显式同意 |
| Word/Excel | **mammoth.js / SheetJS** | 表格 1 万行秒级 | 表格数据不要塞进 PDF 通道 |
| 关键词检索 | **BM25，中文用字符二元组 + 可选 `Intl.Segmenter`** | 10 万 chunk 查询 5–30ms；倒排索引约为原始文本的 30–60% | 中文无空格，纯词级 BM25 会因未登录词崩；二元组是稳妥默认 |
| 语义检索 | **transformers.js + 多语小模型（384/512 维），Int8 量化** | 冷启动下载 30–120MB；吞吐（量级）WebGPU 数百 chunk/s、WASM 数十 chunk/s | 不上服务端 embedding（约束）；不上大模型 embedding（下载不可接受） |
| 向量索引 | **起步暴力余弦 + Float32Array/Int8Array；>5 万 chunk 再考虑 HNSW(WASM)** | 5 万 × 384 维，brute-force 单查约几十毫秒级；常驻内存 Float32 ≈ N×384×4B（5 万 → ≈73MB；30 万 → ≈440MB，**这是内存红线**） | 一上来就上 HNSW 是过度工程：召回调参、序列化、WASM 体积都是成本 |
| 存储-大对象 | **OPFS**（分片文件：`chunks.bin` / `text.bin` / `vec.i8` / `bm25.bin`） | 300 篇正文纯文本约 30–150MB 级 | 不放 IndexedDB（大 Blob 读写性能与事务开销都差） |
| 存储-元数据 | **IndexedDB**（doc / chunk 元数据、映射表、运行记录） | 键值小、事务足 | 不放 localStorage（5MB 上限、同步阻塞） |
| 统计计算 | **Pyodide + statsmodels/linearmodels**（主）＋ JS 手写 OLS/within 变换（快通道） | Pyodide 冷启动约 2–5 秒、体积 10–30MB 级；面板固定效应 + 聚类标准误在 JS 手写风险高 | 纯 JS 手写面板 FE + 聚类稳健标准误 = 自造统计 bug，不值得 |
| 可视化 | **ECharts 或 Vega-Lite**（择一，别两套） | 事件研究图/系数图秒级 | 不手搓 canvas 图表 |
| 本地生成 | **WebLLM（WebGPU）为主，transformers.js 小模型为备** | 模型 0.6–2GB 级下载；WebGPU 不可用即降级 | 不上任何需要密钥的云 API 作为主路径 |

**离线化关键动作**：用 Service Worker 把 **pdf.js WASM / 分词/词表 / 量化模型 / Pyodide wheel** 全部缓存为同源静态资源。
1) 去掉运行时对第三方 CDN 的依赖；2) 首次之后完全离线可跑；3) 避免"用户论文内容发往外部"的隐私嫌疑（**只下载权重，不上传语料**，这句话必须写在 UI 上）。

### 2.3 容量与性能预算（300 篇的诚实算术）

假设：300 篇，平均 15 页，其中 70% 有文本层（其余扫描/图片版）。

| 量 | 估算 | 说明 |
|---|---|---|
| 页数 | ≈ 4500 页 | 纯文本页解析总计约 0.5–2 分钟（Worker 内，分片） |
| 正文文本 | ≈ 60–120MB | 中文 PDF 常带大量空白与页眉页脚，归一化后压缩明显 |
| chunk 数 | ≈ 6 万–15 万（若含扫描件 OCR 则再增） | 按每页 15–30 个 chunk 估 |
| 向量常驻 | 6 万 × 384 × 1B(Int8) ≈ **23MB**；30 万则 ≈115MB | **所以必须 Int8 量化 + 按需分页载入**，Float32 全量常驻是不可行的 |
| 入库总时长 | **纯文本：约 3–8 分钟；含 OCR：30–90 分钟** | 这是本方案最大的体验风险，见 §5 |
| 单次检索延迟 | BM25 5–30ms + 向量几十 ms + 融合 → 目标准 <150ms（P95） | 索引未就绪时只跑 BM25，UI 明示"语义检索未就绪" |
| 存储占用 | 元数据 + 索引 + 文本 + 向量 ≈ **200–500MB**（视语料） | 需 `navigator.storage.estimate()` 预检 + `persist()` 申请 |

### 2.3b 已核验的平台事实（选型的地基，附出处）

标注规则：**【已核验】= 有官方文档/规范出处；【估算】= 我方工程估计，需实测确认。**

| 事实 | 状态 | 出处 |
|---|---|---|
| `FileSystemSyncAccessHandle` 已是 Baseline "Widely available"（2023-03 起跨浏览器可用），但**仅能在 Dedicated Web Worker 内使用**，且只作用于 origin private file system | 【已核验】 | [MDN: FileSystemSyncAccessHandle](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemSyncAccessHandle) |
| 同接口适合"大规模文件更新，例如 SQLite WASM 数据库"；早期规范把 `close/flush/getSize/truncate` 定义为异步，**旧实现可能是异步**（需特性适配） | 【已核验】 | 同上 |
| WebGPU 已跨四大引擎支持：Chromium 113+（Win/macOS/ChromeOS）、Android 121+（Android 12+、高通/ARM GPU）、Firefox 141（Windows）、Firefox 145（macOS Tahoe 26 ARM64）、Safari 26（macOS/iOS/iPadOS/visionOS 26）；**Linux / Intel Mac / Firefox Android 仍在推进** | 【已核验】 | [web.dev: WebGPU is now supported in major browsers](https://web.dev/blog/webgpu-supported-major-browsers)（2025-11-25） |
| Transformers.js（v3）与 ONNX Runtime Web 均已支持 WebGPU 后端 | 【已核验】 | 同上 / [Transformers.js](https://huggingface.co/docs/transformers.js/index) |
| 各家浏览器存储配额/驱逐策略与"persistent 不等于永久"的语义差异 | 【估算/需逐一实测】 | 建议自测 `navigator.storage.estimate()` 与 `persist()` 再写进文档 |

**由此推出的两条硬性结论**：
1. **§4 的"存储接口化"不是可选项**：同步句柄只能在 Worker 内用、且旧实现的异步差异真实存在 → 存储层必须有一个能吸收这些差异的 adapter，否则未来换宿主（Web → Tauri/SQLite）时全站重写。
2. **WebGPU 从"加分项"升级为"可依赖的默认"**：2025-11 起四大引擎均支持（有平台限定）。因此本地生成/本地 embedding 可以做成**默认路径**，但仍必须保留 WASM 回退——Linux 桌面与 Intel Mac 的 Firefox 用户仍会落空。

**三条硬性工程纪律**：
1. **绝不一次性读入全部 PDF**。按页流式抽，抽完即释放页对象。
2. **主线程永不做解析/embedding/统计**。全部 Worker；UI 只收进度事件。
3. **每一步都可中断**。索引清单里每篇文档有状态位（pending/parsing/parsed/failed/ocr-needed），刷新即续。

### 2.4 降级矩阵（这张表建议直接进 demo 的"关于"页）

| 失效条件 | 检测方式 | 降级行为 | 用户可见提示 |
|---|---|---|---|
| 无 File System Access API | 特性探测 | 退回 `<input webkitdirectory>` 批量选择 + 每次会话重新授权 | "本浏览器无法记住文件夹，下次打开需重新选择（索引不会重算）" |
| 无 OPFS（或同步句柄） | 特性探测 | 退回 IndexedDB 大对象 + 内存缓存；容量上限下调 | "存储能力受限，建议语料 ≤100 篇" |
| 隐私模式 / 存储被禁 | 写入探针失败 | 纯会话模式：不落盘，退出即清空 + 强制导出提醒 | 醒目横幅 |
| 存储配额不足 | `estimate()` 预检 + 写入捕获 QuotaExceeded | 停用向量索引（保留 BM25）+ 允许清 OCR 中间产物 | "空间不足：已降级为关键词检索" |
| 无 WebGPU | `navigator.gpu` 探测 | 本地生成关闭 → 转"检索式起草"（模板组装）；embedding 走 WASM | "生成式能力不可用，已切换到检索式起草" |
| 模型下载失败/离线 | fetch 超时 + 校验和 | 关键词-only 模式；主流程不阻塞 | 可重试，附下载体积 |
| 页面在索引中途崩溃 | 清单状态位 + 心跳 | 重启后从最后未完成文档续跑 | "已恢复，剩余 N 篇" |
| 单篇 PDF 解析失败 | coverage/异常捕获 | 标记该篇失败但**不中断整批**；进入"待人工处理"列表 | 失败清单可导出 |
| 语料被浏览器驱逐 | 启动时校验清单与文件 | 提供"导入备份包"恢复；提示重新授权目录 | 需要导出/导入闭环（**必做**） |

**评审意见**：降级矩阵里最容易被漏掉、但最致命的是最后两行——**"单篇失败不拖垮整批"和"驱逐可恢复"**。300 篇里必然有坏文件，一个 try/catch 没兜住就让整个 demo 在评委面前卡死，这是最常见的翻车方式。

## 3. 没有后端时，AI 真调用 / Key / 代码执行如何"诚实演示"

### 3.1 原则：**推理位置必须可见**

在 UI 上常驻一个状态条，实时显示：

```
推理：本机 · WebGPU · Qwen2.5-1.5B-Instruct-q4f16 · 24 tok/s · 本次未联网
检索：本机 · BM25 + 本地向量 · 语料 287 篇 / 8.4 万块
出网：仅下载模型权重（一次性，已缓存）· 你的 PDF 与文稿从未离机
```

这一条状态条的信任价值，远高于任何一个功能。**"我们不上传你的数据"应该是一个可验证的开关式声明，而不是一句宣传语。**

### 3.2 四种模式，分级诚实（按可用性自动选择，用户可强制切换）

| 模式 | 机制 | 诚实标注 | 演示价值 |
|---|---|---|---|
| **A. 本机真推理** | WebLLM / transformers.js，WebGPU 优先 | "本机模型 · 参数与量化已标注 · 可能出错需核对" | 证明"离线可用" |
| **B. 检索式组装**（建议设为**默认演示路径**） | **零神经网络生成**：用检索结果做槽位填充——"研究表明，{作者}({年})基于{数据}采用{方法}发现{结论}[{chip}]" | "检索式骨架生成（非神经网络生成）" | **最稳、最快、可复现、每次结果一致**，且仍然"真的有人在检索" |
| **C. 自带密钥（BYOK）** | 用户粘贴 key，存 `sessionStorage`，直连厂商接口 | "密钥仅存于本页内存，刷新即失效，不经我方服务器" | 证明可对接真实云模型，且我方零密钥 |
| **D. 回放** | 预录制的金标准输出 + 完整 provenance | "这是预录制结果，用于展示目标形态" | 答辩现场断电断网时的兜底 |

**评审意见**：把 **B 设为默认路径**是这个 demo 最聪明的决策。它的输出质量可控、延迟为零、可复现、且**不撒谎**——因为它在 UI 上承认自己不是神经网络生成。同时把 A 做成"可选增强"：跑得动就是惊喜，跑不动也不影响主流程。绝大多数纯前端 AI demo 死因都是"把 A 当主路径，结果在评审的旧笔记本上跑不动"。

### 3.3 密钥问题的正确姿势

- **绝不在交付物里出现任何 key**，包括硬编码、示例值、注释里的"演示 key"。
- BYOK 只写 `sessionStorage`，永不 `localStorage`；UI 明示"刷新即失效"。
- 若要做"无需 key 的云调用"，**只允许**"用户自己提供"或"用户自己付费"的中转（如让用户填自己的 endpoint）。不要用公开免费端点做演示——它会挂，而且会把用户文稿发到你无法承诺的地方。
- **反向要求**：任何模式都必须能一键看到"本次请求将发送什么"（prompt 清单 + 片段预览）。这是"零上传"声明的技术凭据。

### 3.4 代码执行如何诚实

这是四块能力里**最容易造假也最容易被当场戳穿**的一块。诚实做法：

1. **数据来源可见**：用户上传 CSV/XLSX → 展示解析预览 + 行数 + 列类型推断 + 缺失值统计。
2. **代码是文本，可读可改可下载**：生成的不是"黑盒结果"，而是一段完整 Python（或 JS）脚本，UI 左侧脚本 / 右侧结果。
3. **执行是真的**：Pyodide 在 Worker 内跑，输出 stdout/stderr/表格/图。**执行失败也要展示失败**（不要静默吞掉 traceback）。
4. **可复现是承诺，不是措辞**：
   - 脚本自带 `--seed`、数据哈希、`pandas/numpy/statsmodels/linearmodels` 版本锁；
   - 提供"导出可复现包"（脚本 + 数据 + 环境锁 + 运行日志 + 结果哈希）；
   - **一键"重跑并比对"**：同输入必须产出同系数（浮点容差内）。
5. **拒答机制**：当识别策略与数据结构不匹配（如样本期太短、无对照组、面板不平衡严重），应**明确输出"你的数据不支持 DID 设定，理由：…"**，而不是硬跑一个漂亮的表。**在 demo 里主动演示一次"拒绝"，是极强的可信度信号。**

> 评审意见：建议在 demo 脚本里内置一段"**用论文公开数据 + 论文公开系数做交叉验证**"的彩蛋——比如拿一篇经典 DID 论文的复现数据，跑出与原文一致的系数。这一个动作就把"AI 写代码"从"看起来很酷"提升为"**结果可对账**"。

## 4. 若日后做本地 App：哪些决策可复用、哪些必须替换

### 4.1 核心判断

**可复用的是"数据模型 + 契约"，不是"实现"。**
Web demo 与本地 App 的差异，本质上只在**物理存储、推理宿主、文件权限**三处；逻辑层应当 100% 共享。

### 4.2 复用 / 替换清单

| 层 | 决策 | 判定 | 理由与迁移动作 |
|---|---|---|---|
| 领域模型 | `Document / Chunk / Section / Citation / AnalysisRun / Artifact` schema | **完全复用** | 定成纯 TypeScript 类型 + 显式迁移版本号；这是最贵的资产 |
| ID 与幂等 | 内容哈希 + 清单状态机 | **完全复用** | 与宿主无关，且直接决定"可续跑"能力 |
| 解析/归一化 | pdf.js 调用、CJK 归一化、标题聚类规则 | **基本复用** | Rust/Node 侧可换 pdfium/mutool，但**规则集与测试样例必须带走**（建一个 50 篇的黄金语料回归集） |
| 检索融合 | RRF / MMR 融合公式、打分权重 | **完全复用** | 纯函数，抽成无 IO 模块 |
| 存储接口 | `CorpusStore` 接口（put/get/query/list/delete/export） | **接口复用，实现替换** | Web 实现：OPFS+IndexedDB；App 实现：SQLite。**从第一天就面向接口编程**，否则迁移时全站重写 |
| 检索索引 | BM25 倒排 | **实现替换** | Web：MiniSearch/自研；App：SQLite **FTS5**（含 trigram/ICU 分词）。BM25 参数与分词策略复用 |
| 向量索引 | 暴力余弦 → HNSW | **实现替换** | App：sqlite-vec / usearch / LanceDB；**向量维度、量化方式、度量必须锁定**，否则索引无法迁移 |
| Embedding | transformers.js（浏览器） | **可复用或替换** | 若要求质量与速度，App 侧换 ONNX Runtime / llama.cpp embedding。**关键是 embedding 模型 ID + 版本写进索引元数据**，换模型即全量重建（这点在 demo 期就要把"重建索引"做成一个按钮） |
| 本地生成 | WebLLM | **替换** | App：llama.cpp / Ollama / MLX，直接跑 7B–14B，质量跃升。**Prompt 与引用约束层复用**（把 prompt 模板、引用格式校验抽成纯函数） |
| 统计执行 | Pyodide + statsmodels | **替换（收益最大）** | App：真 Python 环境，可装 `linearmodels`/`pyfixest`，性能与包覆盖远超 Pyodide。**生成的脚本本身格式不变**——这是最大的复用红利 |
| 文件访问 | File System Access API / webkitdirectory | **替换** | App：原生目录监听（Tauri/Electron）。**"用户授权目录 + 记住句柄"的交互模型与权限话术复用** |
| 导出格式 | 证据包（zip：md/csv/py/json/哈希） | **完全复用** | 这是跨宿主的数据契约，也是唯一的同步/备份通道 |
| UI 组件 | 编辑器、citation chip、证据面板、进度中心 | **完全复用** | 保持"无宿主依赖"（不直接调 OPFS/`navigator.gpu`，走接口） |
| 并发模型 | Worker 池 + 进度事件 | **部分复用** | App 侧换线程/进程池，但**进度事件协议复用** |
| 安全模型 | 沙箱 iframe 执行、CSP、零上传 | **部分复用** | App 里"零上传"变成默认而非约束；但沙箱执行不可省（用户/模型产出的代码必须隔离） |

### 4.3 为迁移现在就要做的三件事（成本极低、收益极高）

1. **`CorpusStore` / `Retriever` / `Generator` / `Executor` 四个接口先定死**，Web 实现只是其中一套 adapter。
2. **索引元数据里写死"可迁移性头信息"**：`embedding_model_id@version`、`dim`、`quantization`、`tokenizer_id`、`chunker_version`、`schema_version`。没有这些，索引就是一次性垃圾。
3. **黄金语料回归集**：50 篇有代表性的 PDF（含双栏、扫描、中文子集字体、公式、表格），每次改解析或分块都要跑一遍指标。这个集合在迁移到本地 App 时会**直接变成验收测试**。

> 评审意见：如果现在不做第 3 条，迁移时你会发现"新解析器看起来更好，但说不出哪里变差了"，然后陷入无休止的手工比对。黄金语料集是这份方案里**最不性感但最省钱**的投入。

## 5. 反驳与风险（魔鬼代言人）

### R1（最高风险）"纯前端"解决了 demo 的分发问题，却可能摧毁产品的可信度
- **反驳**：demo 与产品不该共用同一套物理架构。demo 要的是"一个链接、零密钥、点开就跑"；产品要的是"300 篇不丢、跑得快、模型够好"。
- **证据**：浏览器存储可被驱逐（"best-effort" 语义下配额压力会清理数据），一旦 300 篇索引在用户第二天打开时消失，无论你解释得多好，用户只会记得"我的东西丢了"。
- **处置**：① 申请 persistent 存储并**如实告知**它并非绝对保证；② 从第一天就做**加密导出包 / 导入恢复**闭环；③ 在 README 与 UI 明确"这是工作台，不是资料库，请定期导出"。

### R2 PDF 解析质量是不可控变量，而整条链建立在它之上
- **反驳**："先上传 300 篇 PDF"听起来是入口，实际是**全部风险的第一现场**。中文 PDF 常见子集字体 + 缺 ToUnicode CMap → 抽出来是乱码；扫描版无文本层；双栏学术排版阅读顺序错乱；公式与表格直接丢失。
- **证据（可自证）**：不需要外部证据，**第一天就用真实语料做 20 篇抽样**，把 coverage / 乱码率 / 阅读顺序错乱率量出来。如果抽样乱码率 > 10%，整个"章节-引文映射"就不成立。
- **处置**：① 语料体检报告前置，**让失败可见**；② 双栏检测 + 分栏重排；③ 乱码页降级为"仅缩略图 + 人工标注"；④ 手工纠正的映射要能存下来、下次复用。
- **底线**：如果抽样结果太差，**应当改变产品定位**（例如从"全自动解析"改为"半自动标注工作台"），而不是硬撑。

### R3 索引构建时长会杀死"交互式 AI 产品"的体验假设
- **反驳**：300 篇（尤其含扫描件）首次入库是分钟到小时级。任何"上传完立刻对话"的期待都是错的。
- **证据**：纯文本 300 篇约 3–8 分钟，扫描件 OCR 可到 30–90 分钟。
- **处置**：① 把它设计成**后台批处理**而不是阻塞式对话框；② 允许"边索引进边用已就绪部分"；③ 提供"只索引摘要/前 N 页"的快速模式；④ 显示预计剩余时间（用已完成文档的实测速率外推，别用假的进度条）。

### R4 本机小模型的文本质量，很可能达不到"论文撰写"的门槛
- **反驳**：0.5B–3B 量化模型写不出可用的学术中文段落，且容易在**引用上编造**——这恰好摧毁本产品唯一的卖点（可核查）。
- **处置**：① **默认走检索式组装**（模式 B），让"有据可查"不依赖模型质量；② 生成后**强制引用校验**：每个 `[n]` 必须映射到真实 chunk，否则标红并降级为"无来源"；③ 明确把目标定位为"骨架与素材编排"，而不是"成品段落"。

### R5 "实证研究设计"存在真实的统计误用风险，而产品会赋予它虚假权威
- **反驳**：如果产品在数据不满足平行趋势时照样输出漂亮的 DiD 表，它就在批量制造错误研究。**这比"功能少"危险得多**。
- **证据**：JS/浏览器侧没有成熟的、经过验证的面板计量库；手写固定效应 + 聚类标准误极易出错（自由度校正、多向聚类、奇异矩阵）。
- **处置**：① 走 Pyodide + `statsmodels`/`linearmodels`，不自造轮子；② 内置**识别策略前置检查**（样本量、组数、前期趋势检验、共同支撑），不满足就拒答并说明理由；③ 报告里强制输出标准误类型、聚类层级、固定效应集合；④ 用一篇有公开数据的经典论文做**系数对账**，作为 demo 的可信度锚点。

### R6 服务条款与合规
- **反驳**：即使用户自带 PDF，"批量解析 + 建立索引 + 提供摘录引用"仍可能触及相关数据库/出版方的使用条款；面向学生群体的学术工具尤其敏感。
- **处置**：① 明确"用户对自己上传内容的合法性负责"；② **不做任何联网抓取**；③ 不提供"导出全文"功能（只导出摘录片段 + 出处）；④ 在 README 里主动写清数据不出本机、不建立可再分发的语料库。

### R7 四块能力并行 = 每块都做不深
- **反驳**：4 块能力 × 完整可用 = 一个小团队季度级工作量；纯前端约束下还要再加解析、OCR、索引、存储、降级五套基础设施。
- **处置**：**按 §1 的收窄方案执行**——一块主流程（语料→索引→章节映射→起草），其余三块作为该流程的三种输出。宁可只有一块做到"可信、可复现、可回跳"，也不要四块都停在"点得动"。

### R8 "演示可信度"本身是可被操纵的
- **反驳**：demo 最容易的作弊是"预置结果 + 精美 UI"。评委可能分不清"真的算了"和"演了一遍"。
- **处置**：**主动做可验证性设计**：① 让评委**现场换一篇 PDF**（不在预置语料里）走完流程；② 现场点 citation chip 回跳；③ 现场改数据重跑并比对系数；④ 提供"随机抽一篇、随机抽一段、随机抽一个引用"的自检按钮。**把"可被突袭检验"写进 demo 脚本。**

## 7. 一句话交付建议

**保留的**：内容寻址的幂等清单、OPFS+IndexedDB 分层存储、BM25+本地向量的混合检索、逐段 citation chip 回跳、Pyodide 可复现执行、证据包导出、降级矩阵、四个宿主无关接口。
**砍掉的**：独立的学习模式 Tab、任何"整库对话"、任何"零幻觉"承诺、服务端/密钥依赖、未被抽样验证的解析自信。
**必须新加的**：语料体检报告、引用强制校验、拒绝回答机制、导入/恢复闭环、黄金语料回归集、demo 内的"随机突袭自检"按钮。

> 最终判断：**在"纯前端"约束下，可信的 AI 演示不是把模型塞进浏览器，而是把"出处"塞进每一个结论。**
> 模型可以小，检索可以土，但只要每个论断都能一键回到原 PDF 的那一页那一块，这个 demo 就比市面上大多数"AI 写论文"可信得多。
